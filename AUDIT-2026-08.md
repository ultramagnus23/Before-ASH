## 1. Design audit

### 1.1 What is genuinely good — do not let a redesign destroy it

- **A real token system.** OKLCH throughout, a modular type scale (`--text-s-minus-2` → `s-5`),
  one shared easing curve. Colors named by *role* (ink / page / rule / foil / cover), not by hue.
- **Contrast was done properly**, with the reasoning left in comments: `--color-ink-faint` was
  darkened off the prototype value because it measured 2.92:1; `--color-error` /
  `--color-error-on-dark` were split out from the vermilion stamp ink for the same reason;
  `AppNav` uses `text-foil-dim` rather than `text-foil/55` precisely because opacity breaks the
  contrast maths. Better than most shipped products.
- **The stamp is a real interaction**, not a checkbox: 420 ms press-and-hold, SVG arc fill,
  `navigator.vibrate(12)`, deterministic per-item rotation (`seedRotationDeg`), a badge with a
  radial mask so the ink sits unevenly, `mix-blend-mode: multiply`. Reduced-motion is handled with
  intent — the hold timing is kept because it is *functional*, only the bounce is dropped.
- **The MRZ strip** on `/list` (passport machine-readable zone encoding handle + stamped count) is
  the single most distinctive element in the product.
- **Progressive enhancement.** Filters are links, not client state. Most pages are server
  components with zero client JS.

### 1.2 Where the design is thin — the real findings

**A. There is exactly one layout, repeated seven times.**
`/list`, `/explore`, `/feed`, `/boards`, `/q/[slug]`, `/u/[handle]` are all the identical
`max-w-[72ch]` cream page on navy: same shadow, same `pt-10`, same mono eyebrow row. A passport has
*different kinds of pages* — a data page, a visa page, an endorsement page, the photo page. Right
now every page is the same page. This is the biggest single reason it reads as flat rather than as
a system.

**B. Every empty state is a dead end.** `/feed`: "Nothing stamped publicly yet." `/boards`: "None
yet." `/u/[handle]`: "Nothing public yet." `/q/[slug]`: "No one's stamped this publicly yet."
`/list`: "Nothing here yet." Not one offers a next action — and given §0 this is what *100% of
visitors currently see* on 5 of 7 surfaces. The empty state is not an edge case here; it is the
product.

**C. The catalog is presented as a phone book.** 491 items as a flat two-column list of
`category — title — [Remix] [Add]`. Nothing ranked, clustered, surfaced, or contextual.
`difficulty`, `group_size`, `locale`, `spice` are seeded on every row, exposed in the TypeScript
type, selected in the query — and **never rendered, never filterable**. Four dimensions of
structure already paid for and thrown away. This is the "not algorithmic" feeling you named, and
it is the cheapest thing on this list to fix.

**D. `/explore` caps at 200 rows** (`query.limit(200)` in `lib/queries/explore.ts`) while the page
header says "491 things, seeded". 291 items are unreachable by browsing. No pagination, no
infinite scroll, no shuffle.

**E. No arrival, no reward, no consequence.** The stamp is a beautiful 420 ms — then nothing. No
sense of a page filling up, no view of the passport as an object, no way in which a 2nd or 50th
stamp differs from the 1st. The MRZ line updating is the entire feedback loop for the product's
stated core action.

**F. `/q/[slug]` and `/u/[handle]` have no `AppNav`.** Follow a link from the feed and you are
stranded with the browser back button. These are also the only two shareable pages — the ones
outsiders land on.

**G. Motion exists in one place only.** Outside the stamp: no page transitions, no list entry
animation, no hover state worth the name, no scroll response. `--ease-passport` is defined once
and used almost nowhere.

**H. `/` (the cover) is doing very little.** A headline, a paragraph, an email field, and a ticker
that is **currently empty** because there are zero completions — so the one dynamic element on the
landing page renders as nothing. The first impression today is a near-blank static page.

**I. Accessibility gaps that survived the audit.** `aria-pressed` on `<Link>` elements in
`filters.tsx` (not valid for a link role); keyboard stamping falls back to `window.confirm()`; the
`toast()` implementation needs verifying as a live region; the visibility `<select>` is a bare
control in a dense row.

**J. Fixed dark chrome, no theme.** `body` is hardcoded to `--color-void`, no
`prefers-color-scheme` handling, no light/dark switch. Defensible as art direction — worth being a
*decision* rather than an omission.

### 1.3 The tension you must resolve before any work starts

`BUILD-PROMPT.md` §2–3 locks the tone as **"dry, second-person, short. The app is not excited for
you. `Stamped.` not `Congratulations!`"** and explicitly **bans**: glassmorphism, gradient text,
identical card grids, hero-metric blocks, spinners, emoji, confetti, **streaks, badges, points,
mascots**.

You are now asking for *fun, exciting, innovative, modern*. Read literally, those collide.

They only collide if "fun" means gamification chrome. The reconciliation — and this must be stated
explicitly in the build prompt so the implementer does not guess:

> **Delight comes from material craft, density, and surprise. Never from points, streaks, badges,
> confetti, or exclamation marks.** The stamp already proves this works: it is delightful *and*
> completely dry. Everything new must clear that same bar.

"Algorithmic" likewise should mean *the product visibly thinks* — ranking, clustering, semantic
neighbours, "three people also have this open", a generated weekly page — not a recommendation
feed with engagement mechanics.

## 2. Content audit

### 2.1 The catalog (491 items)

| category | n | category | n | category | n |
|---|---|---|---|---|---|
| campus_ritual | 42 | academic | 42 | people | 42 |
| creative | 38 | delhi_ncr | 38 | career_money | 36 |
| food | 35 | body_sport | 35 | chaos | 34 |
| service | 30 | solitude | 27 | night | 26 |
| legacy | 24 | skills | 22 | admin_life | 20 |

Fields per item: `title, category, difficulty, group_size, locale, spice, id, slug`.

**Findings:**

1. **12 items still carry `placeholder: true`** — generic phrasing where a real Ashoka building,
   mess, or room name belongs: CP-1001, CP-1003, CP-1007, CP-1009, CP-1018, FD-1041, FD-1048,
   PP-1057, CP-1213, CP-1226, FD-1254, AD-1485. `BUILD-PROMPT.md` §5 calls this "the
   highest-leverage hour on the project" and says it needs a campus insider — you, not a model and
   not a web search. **Still not done.**
2. **Title only.** No description, no "what this actually involves", no time estimate, no cost, no
   best-season or best-time-of-day, no related items, no prerequisites. A one-stop bucket-list
   product needs a second layer of substance per item; today `/q/[slug]` has nothing to show but
   the title and an empty stamped-by list.
3. **No editorial groupings.** No curated sets ("your first week", "one free afternoon", "monsoon
   only", "do this alone", "before finals", "the last month"). Boards exist as a *feature* and ship
   with **zero** official boards — mechanism built, unused.
4. **difficulty / spice / group_size / locale are unused** outside the DB (finding C).
5. **No seasonality or time-awareness** in the schema, despite the campus calendar being the most
   obvious ranking signal available.

### 2.2 Everything else is empty

Zero `list_items`, `item_posts`, `boards`, `connections`, `reactions`. `getTickerPreview()` returns
nothing. The Wire is empty. Every profile is empty. Every quest page says "No one's stamped this
publicly yet."

This is a **cold-start problem, not a content-volume problem.** Another 500 catalog items would not
change one of those zeroes. The catalog is already the only full thing. What is missing is (a)
depth per item, (b) editorial structure over items, and (c) an honest answer for what the social
surfaces show on day one.

Seeding fake completions or fake users would break §8's privacy posture and the product's whole
credibility premise. The cold-start answer must be editorial and structural, not fabricated.

### 2.3 "One-stop for anything bucket-list" vs. locked scope

`BUILD-PROMPT.md` §5 locks scope to **Ashoka only until 300 weekly actives**, reasoning that a
campus of 3,000 needs ~300 actives for a feed to feel alive whereas a general social app needs
millions. "One stop for anything you'd ever require for a bucket list" is a different, larger
product. Both are legitimate; they are not the same build. **You have to pick before work starts**
— it changes the catalog, the copy, the auth gate, and the ranking model.

- **(A) Stay Ashoka-deep.** Catalog gets richer per item, not broader. Keeps the domain gate.
  Fastest path to feeling alive.
- **(B) Two-layer catalog.** A universal layer (travel, skills, money, health, relationships,
  once-in-a-lifetime) plus a campus layer on top. Makes Ashoka the *first* campus, not the only
  one. Scales, dilutes specificity, needs the auth gate rethought.
- **(C) Ashoka now, architected for (B).** Add the fields and structure a general catalog would
  need; ship the campus one. Small cost now, avoids a rewrite.

Recommendation: **(C)** — satisfies the "one stop" ambition without breaking the 300-actives thesis
or forcing an auth-gate change this month.

## 3. Priority order (highest leverage first)

1. Backfill the 491 embeddings — search is advertised and dead.
2. Fill the 12 placeholders — needs you, one hour.
3. Rebuild every empty state into a first-run experience.
4. Surface difficulty / group_size / locale / spice as real filters and visible metadata.
5. Remove the 200-row cap; add browse affordances (shuffle, dice, "surprise me").
6. Differentiate the seven page layouts within one material system.
7. Add depth-per-item (the second content layer) plus curated official boards.
8. Give the stamp a consequence beyond the row it sits in.
9. Fix the a11y gaps (aria-pressed on links, keyboard stamp, toast live region, select label).
10. Decide A / B / C.
